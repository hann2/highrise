# Tests

Playwright end-to-end tests that run the real game in headless Chrome (with GPU).

- `npm test` — smoke test. Run this after any non-trivial change; it is the main way to tell "compiles" from "works". It boots into the lobby (title, elevator, swapping characters, the pause menu and credits), takes the stairs into the run, moves, picks up a gun and shoots a zombie, swings the doors, checks physics sanity, pauses, browses the encyclopedia, sprints, changes levels (taking a rescued survivor out through the exit stairwell), shops at the second floor's store and leaves its arrival room, checks that player stats take effect, changes settings from the pause menu (render scale with the keys, auto-pause with the mouse), and ends the run by letting the leader die, then goes back to the lobby and opens the encyclopedia from its bookcases.
- `tests/arena.spec.ts` (part of `npm test`) — the arena scene: a loadout and wave from the URL, act scaling, the setup panel rewriting the URL, respawning.
- `npm run test:physics` — node tests for `src/core/physics` (`tests/physics/`). No browser, runs in about a second. Several tests pin exact numeric results; if you change solver/integration behavior on purpose, re-record them with `PHYSICS_RECORD_PINS=1 npm run test:physics` and paste the output into `PINS`. If you didn't mean to change behavior and a pin fails, you broke something.
- `npm run test:core` — node tests for the game loop's frame pacing (`tests/core/`): measuring the refresh rate (dropped frames, loading, power saving, raises that don't hold) and how many frames each animation frame callback runs; for keyframe animation (`src/core/animation/`): sampling tracks, stretching, events and blending; and for the walk cycle (`Gait`): a foot on the ground never moves (at any speed, speeding up, slowing down, curving and turning back), the feet take turns and keep pace, one is always down walking, stopping and turning on the spot step them back under the hips, a teleport isn't a step, and the hips face the right way walking backward, sideways and diagonally; and for things that swing (`Dangle`): left alone it hangs at rest, it lags setting off and swings on stopping and turning, then settles, drag makes it trail, it keeps within its limits, it's the same at 60 and 144 fps, and a long gap or a teleport puts it back at rest; and for things that bend (`DangleChain`, `chainStrip.ts`): it hangs straight left alone, turning the end lags behind the root, it's the same at 60 and 144 fps, and its strip is straight along a straight chain and keeps its width round a bent one; and for cloth hanging from the waist (`hemCloth.ts`): left alone it hangs at rest, walking trails the back out, spinning flares it within the cloth's reach, a leg striding through pushes it out round the leg, it's the same at 60 and 144 fps, and a teleport hangs it at rest.
- `npm run test:footprints` — node tests for bloody footprints (`tests/footprints/`): a spill covers its circle and dries steadily until it's gone, overlapping spills keep the wetter, older blood soaks shoes less and dried blood not at all, a shoe that steps in blood (and the other, less) leaves fainter prints until it's clean, each shoe prints its own side, and clean shoes on a clean floor don't make the floor's stains.
- `npm run test:vision` — node tests for the vision polygon and mesh (`tests/vision/`). They build small scenes of boxes and check what is visible, so add a case there when you touch `visibility.ts` or `visionMesh.ts`.
- `npm run test:characters` — node tests for the character data (`tests/characters/`): every sound and weapon a `characters/data/*.json` names exists and its look is valid, enabled clips' files are in `resources/` and disabled ones in `assets/source/voices/`, no character audio file is missing from its JSON, and `Character.ts` loads every data file. `characterStore.test.ts` tests the character editor's file handling (enabling/disabling moves files, generating, deleting, refusing bad data) in a temporary folder with speech generation faked.
- `npm run benchmark` — seeded frame-time benchmark. Benchmarks run without vsync, with `?fps=120` (`loadGame(page, seed, { fps: 120 })`): every animation frame callback runs one frame of 1/120 s of game time, so the game runs as fast as it can, frame rates can be over 120, and frame intervals are what frames cost, CPU and GPU (before 2026-10-01, Pixi's ticker drew the stage on every callback too, so older numbers aren't comparable). `measureFrames` times the frames the game runs. Writes `tests/output/benchmark.json` with `loopCpuMs` percentiles and a `profile` breakdown (per section and per entity class, ms per frame) and prints the breakdown as a table. Numbers are only comparable on the same machine. `captureProfile(page, ms)` in `helpers.ts` gets the same breakdown from any test or script; timing each entity inflates totals with many entities, so `{ entityDetail: false }` gets accurate per-layer totals without the per-class split. It also returns `gpu`, the GPU ms per frame of the whole render from `GpuProfiler` (`gpuDetail` splits it into sections, which inflates it; see the root `CLAUDE.md`). The lighting benchmark prints GPU time per variant, and the fire benchmark lit and unlit (`gpu/f`), so what lighting costs the GPU is the difference. Both run at resolution 1 by default; `DPR=2` gives the page a retina display's two pixels per point (resolution 2, as a Mac plays at Medium) and `SETTINGS=renderScale=0.5,...` sets the game's settings by id (`src/highrise/settings/settings.ts`), with the results' files suffixed (`-dpr2`, `-renderScale-0.5`). That's how to measure what a graphics setting costs. At resolution 2 the fire scenes are bound by the GPU's pixel work, and the CPU times go up too, since they include waiting for the GPU (`DISPLAY` and `useDisplay` in `helpers.ts`).
- `npm run benchmark:enemies` (`tests/enemies.benchmark.spec.ts`, also run by `npm run benchmark`) — enemy count scaling: waves of 50 to 800 zombies (`ENEMIES=...` overrides) spread over the arena's `hall` (`arrival=spread&layout=hall&god`) with the player standing in the middle and lighting and vision off. It runs with `?fps=120` (as fast as it can), and reports the frame rate it managed, simulation cost per tick, render cost per frame, each tick layer's ticking and rendering, and `frame60` (a 60th of a second of ticks and a render, the CPU a 60 fps frame needs). Writes `tests/output/enemies-benchmark.json`; compare with `tests/reference/enemies-benchmark-*.json`, back to back on the same machine.
- `npm run benchmark:fire` (`tests/fire.benchmark.spec.ts`, also run by `npm run benchmark`) — fire and lighting scaling: 0 to 32 pools of endless fire (the arena's `fires` option; `FIRES=...` overrides) over the `offices` layout (the hall's size in rooms with doorways, with about the walls per light of a real floor), with `dark&fog` as on a floor and the player in the middle. For each count it measures the frames with everything on and again with lighting and vision off (frame intervals include GPU time, so the difference is the lighting's whole cost), and reports burning cells, lights, lights in view and their shadow shapes on average (and the shadow shapes in the whole level), the lighting sections per frame, and the biggest sections. `LAYOUT=sprawl` runs it on a layout sixteen times the size, with as many fires per square meter (64 to 512), and `NEAR=1` keeps the fires in an offices-sized area around the player (the arena's `fireArea`), for what a big level's far walls cost with the same lights in view. `DOORS=1` puts a door in every doorway (the arena's `doors`) and also measures each count with every door being kicked open over and over (the static lights near them drawn again), against at rest. Writes `tests/output/fire-benchmark.json` (`fire-benchmark-sprawl.json`, `-near` for the others); compare with `tests/reference/fire-benchmark-*.json`.
- `npm run test:electron` — the desktop app (`tests/electron/`, its own Playwright config, not part of `npm test`). Packages the app first, then launches the built app hidden with a throwaway save folder (boots over `app://`, keeps the save across a relaunch, gets to the lobby, quits from the pause menu) and smoke-launches the packaged `.app`.

The Playwright tests start their own dev server on port 3456, so they can run while `npm start` is running. `TEST_PORT=3460 npm test` uses another port, so several checkouts can test at once. To keep one dev server across runs, start `npm run dev-server -- --port 3460` yourself and run with `TEST_REUSE_SERVER=1 TEST_PORT=3460`.

## How tests drive the game

- `?seed=123` in the URL seeds `core/util/Random.ts`, making level generation reproducible.
- The lobby and the run plan are reseeded with `seed + 1000` when the lobby is built. Levels are reseeded with `seed + levelNumber` right before generation, so everything generated for a level is reproducible regardless of what happened earlier in the run. The smoke test asserts a fingerprint of `LevelController.level.entities` for level 2 (the run's second floor) against `LEVEL_2_FINGERPRINT`; when you change level generation on purpose, paste the new value from the failure message. If it changes when you didn't touch level generation, something is consuming randomness nondeterministically (see the randomness note in the root `CLAUDE.md`).
- `run.spec.ts` climbs a run with the level cheat to the floors the run plan shapes (with seed 12345: act 1's keycard floor 3, the big store on 5, the boss on 8). `RUN_PLAN` in the smoke test pins the plan's floor names; the keycard floor it expects changes with the plan.
- `tutorial.spec.ts` boots with the tutorial unplayed (every other test marks it played in `loadGame`): Enter at the title starts the tutorial, dying restarts it, and finishing it goes up to the lobby.
- The store's shelf in each arrival room is dealt right after the level is generated, so it is seeded too. `STORE_SHELF` pins what level 2's store sells; it changes when the item pool or rarity weights change, or when what the leader carries out of level 1 does (paste the new value).
- `window.DEBUG.game` exposes the `Game`. Tests find things with `entities.getById(...)` (`lobby`), `entities.getTagged(...)` (`human`, `zombie`, `lobby_character`, `directory_plaque`, `store_machine`), and by class name (see below).
- `loadGame` waits for the title screen (the lobby is only built once you press Enter); `arriveInLobby` presses Enter past the title if it's up and waits for the elevator to open; `startGame` does that and then puts the player on the lobby's stairs, which starts a run as whoever they are (the first unlocked character, Andy, in a new save), and waits for a floor with zombies. The benchmarks use it too.
- Tests reach into entities by class name (`e.constructor.name === "Door"`), which only works in development builds where names aren't minified.
- Dev-only cheat keys from `CheatController` are used for flow control: `KeyL` completes the level (`Shift+L`: kills every enemy), `KeyV` toggles the vision mask, `KeyK` gives the party 5 quarters, `KeyU` unlocks every character (`Shift+U` locks all but the defaults again), `KeyJ` drops an AR-15 at the leader's feet, `KeyN` / `KeyB` / `KeyX` give the leader frag grenades / flashbangs / molotovs, `KeyZ` a health pack (`Shift+Z`: a stim pack), `KeyI` fills the leader's ammo reserves, `KeyH` heals every human, `KeyT` sets fire to the enemies and any fuel near the cursor, `KeyY` spills fuel at the cursor (`Shift+Y`: a trail of it from the leader to the cursor), `Backquote` toggles the fire debug overlay (smoke per cell, the walls smoke sees, and the cell under the mouse).
- Any `pageerror` or `console.error` fails the test. Don't log errors for non-error conditions.

## Philosophy

Browser startup and asset preloading are slow, so prefer one long scenario with many assertions over many small tests. Add assertions to `smoke.spec.ts` rather than adding new spec files unless the scenario is genuinely different.

## Screenshots

Tests write screenshots to `tests/output/` (gitignored). `tests/reference/` holds committed screenshots of known-good output for the same seed, and benchmark numbers from before and after the engine port (same machine). They are for comparing by eye (or by an agent reading the images) after rendering changes — they are not pixel-diffed, because effects and AI are not frame-deterministic. When rendering changes intentionally, copy the new output over the references.
