# Highrise

Top-down 2D zombie shooter for the browser and, through Electron, the desktop. TypeScript, Pixi.js v8 (rendering), a custom 2D physics engine, Web Audio, bundled with Vite. The web version is deployed to Vercel.

`src/core/` is Simon's shared game engine, copied per game. It descends from `simonbw/game-engine` (entities, events, rendering, io, sound) plus the physics engine from `simonbw/tack-and-trim`, stripped down to general-purpose 2D. When fixing engine bugs here, consider whether they should be upstreamed, and add them to `notes/upstream.md`, the list of what's waiting to go back.

## Commands

- `npm ci` — install (Node version in `.nvmrc`)
- `npm start` — dev server at http://localhost:1234, plus a watcher that regenerates the asset manifest, plus the character editor's server (the editor is at http://localhost:1234/tools/character-editor/)
- `npm run build` — production build to `dist/`; `npm run preview` serves it at http://localhost:4173
- `npm run tsc` — type check. Vite does not type check, so always run this after changes
- `npm test` — Playwright smoke test that boots and plays the real game. Run after any non-trivial change; see `tests/CLAUDE.md`
- `npm run test:physics` — fast node tests for the physics engine. Run after touching `src/core/physics`
- `npm run test:vision` — fast node tests for the visibility geometry in `lighting-and-vision/visibility.ts` and `visionMesh.ts`
- `npm run test:core` — fast node tests for the game loop's frame pacing (`core/FramePacing.ts`), keyframe animation and the walk cycle (`core/animation/`)
- `npm run test:characters` — checks the character JSON against the files on disk, and tests the character editor's file handling. Run after touching `characters/data/`, moving character audio, or changing `bin/character-editor/`
- `npm run test:footprints` — fast node tests for bloody footprints: what's spilled on the floor (`effects/SpillGrid.ts`) and what shoes pick up and leave (`creature-stuff/Shoes.ts`)
- `npm run clip -- [--scene fire|deaths|rig|walk|flash|looks] [--seconds 6] [--fps 60] [--size 1280x720] [--dpr 1] [--crf 12] [--port 1234] [--query "floor=wood"] [--out file.mp4] [--keep-frames]` — records a few seconds of a test scene (`?scene=fire&auto`, the default, `?scene=deaths&auto`, `?scene=rig&auto`, `?scene=walk&auto`, `?scene=flash&auto` or `?scene=looks`) from a running dev server to an mp4 in `tests/output/`, plus a contact sheet of its frames. For showing effects and animations without playing. It's recorded a frame at a time, not as a screen recording: it stops the game's loop (`Game.manualFrames`), runs each frame at exactly `fps` (`Game.stepFrames`) and screenshots it losslessly, so every frame is there, evenly spaced, however slowly they're drawn; then encodes H.264 at `crf` (lower is better). `--dpr 2` records at twice the size, as on a retina display, and `--keep-frames` keeps the PNGs
- `npm run benchmark` — seeded frame time benchmark, with a CPU profile of where the loop time goes. Also runs the lighting benchmark, which measures the frame cost with lighting and/or vision turned off. Benchmarks run without vsync, so their frame intervals include GPU time
- `npm run benchmark:enemies` — how the game scales with the number of enemies: waves of 50 to 800 zombies (`ENEMIES=100,400` picks others) in the arena's `hall`, with lighting and vision off, reporting tick and physics cost per tick, render cost per frame, and the biggest sections for each count. Also part of `npm run benchmark`. The baseline is in `tests/reference/enemies-benchmark-*.json`
- `npm run benchmark:fire` — how the game scales with fire: 0 to 32 pools of fire that never go out (`FIRES=8,32` picks others) over the arena's `offices` (rooms with doorways: a real floor's wall density, since shadows cost by the walls near each light), dark and with fog of war, reporting burning cells, lights (and how many are in view, which are the ones drawn), frame rate and CPU with everything on and with lighting and vision off, and the lighting sections (packing the atlas, the mask and light passes, the composite). `LAYOUT=sprawl` runs it on the huge layout (with as many fires per square meter), and `NEAR=1` keeps the fires in the offices' area around the player, so only the level's size differs. `DOORS=1` puts a door in every doorway, and also measures each count with every door kicked open over and over. Benchmarks run at resolution 1; `DPR=2` runs them as on a retina display (resolution 2), and `SETTINGS=renderScale=0.5,...` with those settings. Also part of `npm run benchmark`. The baseline is in `tests/reference/fire-benchmark-*.json`
- `npm run electron -- [play=chad floor=5]` — the desktop app in development: Forge starts its own Vite dev server (port 1236, so it can run next to `npm start`) and opens the game in an Electron window. `key=value` arguments become the page's query string
- `npm run package` — packages the desktop app into `out/Highrise-darwin-arm64/Highrise.app` (macOS only for now); `npm run make` also zips it
- `npm run test:electron` — packages the desktop app, then tests it (`tests/electron/`): the build boots over `app://`, keeps its save across launches, plays and quits; the packaged app gets to the title
- `npm run prettier` — format `src/`
- `npm run generate-manifest` — regenerate `resources/resources.ts` after adding/removing assets (`npm start` does this automatically)

## Layout

- `src/core/` — game-agnostic engine. Must not import from `src/highrise/` (type-only imports via `src/config/` are the one exception)
  - `Game.ts` — main loop, entity add/remove, event dispatch, pause, slow-mo. One frame (a tick and a render) per display refresh, with `dt` the ideal frame time (`FramePacing.ts`: `RefreshRateEstimator` measures the refresh rate from animation frame timestamps, and keeps measuring, so power saving or another display changes it; the desktop app reports the display's own rate through `window.desktop`; `FramePacer` decides how many frames each callback runs: skips some under a frame rate limit, catches up at most 3 after a dropped frame, then lets the game slow down). `frameRateLimit` is the player's limit (the Frame Rate Limit setting); below 60 fps each frame runs more than one tick. `?fps=120` pins the refresh rate instead of measuring it and makes every animation frame callback one refresh, which the benchmarks use since they run without vsync: the game runs a frame per callback, as fast as it can, so frame intervals are what frames cost (and can be under 8.33 ms). `manualFrames` stops the loop altogether and `stepFrames(n)` runs frames by hand, for recording video a frame at a time. `simulatedTime` is the seconds of ticks run while not paused (so slow-mo slows it), for bringing looks up to date in `onRender` by how much happened since the last frame
  - `entity/` — `Entity` interface, `BaseEntity` base class, event type maps
  - `animation/` — keyframe animation that doesn't know what it animates: a `Track` is keyframes of a value with easings (`easing.ts`), sampled as numbers, vectors, steps, or segments the caller interpolates itself; an `Animation` is tracks plus timed events; `AnimationPlayer` plays one at a time, stretched to a duration, fires its events as game time passes them (advance it in a tick), and blends from what was showing (the last animation held where it was, or the rest pose) when its owner samples it with `pose(sample, rest, blend)`. `Gait.ts` is a walk cycle for two feet that's worked out rather than played: each `update` takes where the body is, which way it faces and the game time since the last one. Each foot has a place on the floor (`feet`), and one that's down never moves, however the body speeds up, slows down or turns, until the step cycle (`phase`, moved on by the distance the body goes, so pausing and slow motion need nothing) lifts it; then it swings to where its hip will be when it lands plus its reach, and comes down there, calling `onLand` (side, where, which way it points, speed, and whether it was a `settling` step), which is what footprints and footsteps can hang off. Standing, feet out of place step back under the hips one at a time, which is also how it turns on the spot; a teleport puts them under the body without a step. Steps get longer and spend less time on the ground with speed (`GaitStyle`), the feet step along the direction of travel, and the hips turn toward it, at most 60° from facing, so walking backward steps backward and sideways crab-steps
  - `graphics/` — Pixi renderer wrapper, layers, camera
  - `ReactEntity.ts` — an entity that renders Preact content into a `div` over the canvas, re-rendered every frame
  - `physics/` — custom 2D rigid body engine (see its `README.md` and `CLAUDE.md`)
  - `io/`, `sound/`, `resources/` (preloader), `util/` (profiler, `stats-overlay/`, random, math)
- `src/config/` — configures core for this game: render `Layer`s, `CustomEvents`, `CollisionGroups`, `PhysicsMaterials`
- `src/highrise/` — the actual game
  - `main.ts` — bootstraps `Game`, preloader, and global controllers
  - `controllers/` — long-lived entities driving game flow (`GameController`, `LevelController`, ...). The flow: boot → `goToLobby { from: "boot" }` → `menu/TitleScreen` (on black, with no world yet) → Enter builds `lobby/Lobby`, or the first time (until `localStorage.tutorialComplete`) dispatches `startTutorial`, a run of just level 0 (dying restarts it, the pause menu can skip it) that ends with `goToLobby { from: "tutorial" }` → the lobby's stairs dispatch `newGame { character, plan }` → `LevelController` plays the plan's floors (1..n) → `gameOver` → `menu/GameOverScreen` → `goToLobby { from: "run" }`
  - `lobby/` — the hub between runs and the diegetic main menu. `Lobby` builds the hand-made lobby (`levels/level-generation/lobbyGeneration.ts` + `levels/rooms/LobbyRoomTemplate.ts`, which holds the layout), puts the player in the arrival elevator (a ride up: fade in from black, a little camera shake via `Camera2d.shakeOffset`, a bump as it stops, then the doors open; shorter after a run), and stands every rescued character around (`LobbyCharacterController`: E swaps into them; characters not rescued yet aren't in the lobby at all, and newly rescued ones turn up while it's open). Also `ReceptionistBob` (a harmless heavy) and the encyclopedia bookcases. The run ahead is deliberately not shown in the lobby: from the second floor on, the spawn room has an `environment/DirectoryPlaque` that opens `menu/FloorDirectory` (the `RunPlan` with "You are here", game paused). No enemies and no run HUD (only the big version of `hud/InteractPrompt`), but fog of war: the lobby's explored map is unexplored the first time and then kept in `SaveData.lobbyExplored` (a PNG data URL, saved every 10 s and when the run starts) via `VisionController.resetExplored`/`exportExplored`. It's hidden (`VisionController.exploredDarkness` at 1) while the elevator is shut and comes into view as the doors open
  - `run/RunPlan.ts` — `generateRunPlan()`: the run's 15 floors in order (`FloorPlan`: number, act, template, name, directory notes, landmark, keycard, big store, gun tier), made when the player arrives in the lobby. `run/acts.ts` holds the run's shape and everything that scales with it: acts of 4 floors, landmark floors 4/8/12/15 (sieges on 4 and 12 are plain generator floors until the siege exists, bosses on 8 and 15), one keycard floor per act, big stores (8 items) on 5/9/13, the gun tier each act's stores deal from, enemy counts per floor, and per-act enemy HP and damage (applied in `BaseEnemy.onAdd` and `inflictDamageFrom`). `LevelController` hands each template its `FloorPlan` (`template.floor`). A boss's death dispatches `bossDied`, and `controllers/BossRewards` drops its loot: quarters, throwables, a usable and an item from `items/bossItems.ts`. Level templates carry `floorName`/`floorNotes` for the directory. The level number is the floor number
  - `levels/level-generation/` — procedural generation (room placement → maze → walls → doors → closets/nubbies → entity placement); `level-templates/` define per-floor themes; `rooms/` define room templates. The lobby skips all that but the room and walls (`lobbyGeneration.ts`)
  - `human/`, `characters/`, `enemies/`, `weapons/`, `projectiles/`, `environment/`, `effects/`
  - `enemies/remains/` — how zombies, sprinters and crawlers die. `BaseEnemy.die(killer, blow)` gets a `DeathBlow` (kind, direction, where it hit, and `recentDamage`, so a shotgun's pellets add up), and `chooseDeathStyle` picks by damage and which part the blow's path crossed (`hitPart`: from above the head is in the middle, the arms at the sides): fall over, head popped (bullet) or knocked off (swing), an arm off, cut in half, or blown apart. `comeApart` makes the `Corpse` (falls from the `BodySprite`'s last pose to lying down, using the crawler's textures plus legs, in a pool of blood that spreads; keeps burning and charring if it died on fire) and the flying `Gib`s (fake height like `FleshImpact`, bounce off walls, leave blood), which settle into `Remains`. Corpses and remains stay for the floor and cost nothing per frame. A zombie that crawls on leaves its legs. The lying torso and legs are drawn from the zombie's look (`looks/`), like the rest of it. `?scene=deaths` (development only) is a lineup killed each way (`DeathsTestScene`; `?auto` repeats it for `npm run clip -- --scene deaths`)
  - `characters/data/<id>.json` — each character as data (the format is `CharacterData` in `characters/CharacterData.ts`), which the character editor writes: name, description, `look` (what their body is drawn from, see `looks/` below; it includes the trouser and shoe colors), `stats` (overrides to the neutral `PlayerStats`, applied when the `Human` is made), `startingWeapons` (weapon names; everyone has a pistol for now; the leader starts a run with them, since the arrival room has no guns, and a survivor carries them), the ElevenLabs voice, and voice `clips`. A clip is one audio file with its transcript (`text`, with ElevenLabs v3 tags like `[sighs]`; empty if not transcribed), the events it plays on (`categories`), its source (`recorded` or `elevenlabs`) and `enabled`. Enabled clips' files are in `resources/audio/characters/<id>/` and ship; disabled ones are in `assets/source/voices/<id>/`, kept in git for comparing. `Character.ts` imports every data file and builds `Character.sounds` from the enabled clips. JSON isn't type checked, so `characterDataProblems` checks the names in it (and `lookProblems` the look): at load in development, and in `npm run test:characters`. Enabling or disabling a clip means moving its file and regenerating the manifest
- `src/tools/character-editor/` — the character editor, a dev-only Preact page (a second entry of the dev server, not in `npm run build`), in three tabs (the last one used is remembered): Appearance (every setting of the character's look, with a live preview drawn by the game's generator, standing, lying and part by part; a random look, a new seed, and a preview as a zombie), Gameplay (starting weapons and stats), and Voice (the ElevenLabs voice, and their clips by category, where you can play, enable/disable, fix the text, change categories, transcribe, delete, and generate new takes of a line or variations of a clip (they come in disabled)). Edits to a character (name, description, look, weapons, stats, voice) are a draft until saved (`drafts.ts`): a bar at the top says what's unsaved, with Undo, Redo, Revert (which Undo brings back), Save (⌘S) and Save all; tabs and the sidebar mark what has unsaved changes, leaving the page warns, and drafts are kept in localStorage so a reload doesn't lose them. Clip changes are files, so they still happen right away. It talks to `bin/character-editor/server.ts` (127.0.0.1:1235, run by `npm start` or `npm run character-editor`) through the dev server's `/api` proxy (`vite.config.mts`); `CHARACTER_EDITOR_PORT` moves both, so a second checkout can run its own. The server does every file change through `CharacterStore`, which checks the data with `characterDataProblems` before writing, and makes the ElevenLabs calls (`elevenLabs.ts`) with `ELEVENLABS_API_KEY` from the environment or `.env` (gitignored), so the key never reaches the browser. Generated takes are `eleven_v3`, trimmed and leveled by `audioProcessing.ts` (silence off both ends, one gain change to -24 LUFS with peaks under -1.5 dBTP) and saved as `<id>-<category>-<n>.flac`; the ✂ button does the same to any clip in place, and ↗ opens a clip in Ocenaudio (`AUDIO_EDITOR` overrides the app)
  - `human/Human.ts` carries two weapon slots that take anything (`weapons`, `activeSlot`; a new weapon fills an empty slot, else replaces the one in hand, see `slotForNewWeapon`), a reserve of rounds per ammo class (`weapons/guns/ammo.ts` has every ammo constant and price; every class runs out, `Gun.reload` takes from the shooter's reserve), one type of throwable (`consumable`, `weapons/consumables/`: thrown with G by `ThrownConsumable`, goes off as an `effects/Detonation`), and one usable (`usable`, `weapons/usables/`: health packs and stims with charges, used on yourself with C / RB; `applyTimedStats` is how a stim's boost wears off). Holding Shift / LT while moving sprints (`Human.sprinting`, set by `PlayerHumanController`): faster, but no using the weapon or reloading unless `PlayerStats.canShootWhileSprinting`. Guns are only bought (the arrival room's store, and the keycard armory); closets have melee weapons, ammo, health, throwables and usables. Floor vending machines (`environment/furniture-plus/VendingMachine`, at most `MACHINES_PER_FLOOR` on a floor, in nubbies) are snack (health), ammo (a box for the gun in hand) or grenade machines
  - How a human holds a gun is `weapons/guns/GunPose.ts`. A gun's `points` (grip, foregrip, magazine, action) are in its own frame: meters from the middle of its holding image, x toward the muzzle. `poseGun` builds the gun's transform in the holder's frame from its parts in order (`holdPosition`, the animation playing, recoil, a wall in the way, `sideOffset`, a push) and puts the hands on points of the gun (so they go wherever it goes) or at places on the body. `Gun.getPose(push, twist)` is that pose with the gun's animation blended, and `HumanSprite` works it out once per frame, before posing the body; it also draws the magazine in the left hand and the left hand over the gun when the animation says so. A gun's `animations` (`GunAnimations`, per family in `weapons/guns/gun-animations/`: the reload, from empty, the parts of a round-at-a-time reload, the pump) are `core/animation` `Animation`s of `GunTracks` (the gun's offset and angle, each hand's target, where the magazine is) with `GunEvent`s (sounds, or a piece of one, the gun's own sounds, dropping the magazine). They're visual and play the sounds; the gameplay's timing is still `GunStats` and `Gun.reloadAction`, and each animation is stretched to the time its part takes (`Gun.animationDuration`), so reload speed items stretch them, sounds and all. Reload recordings are played a piece at a time, each on the motion it's the sound of. The magazine images are placeholders drawn as SVG (`assets/source/magazines/`, `bin/render-svg.ts`)
  - `rig/` — `?scene=rig` (development only): a lineup of humans, one per gun, shooting a little and reloading over and over, for making and looking at animations. `anim=reload` (or M) plays one of the guns' animations over and over instead, `points` (G) marks each gun's points and rings the hands, the number keys set the speed, Space pauses, `.` steps a frame, and the arrow keys scrub the animations while paused. `gun=`, `character=`, `columns=`, `zoom=` and `speed=` in the URL; `npm run clip -- --scene rig --query "gun=ar15&anim=reload"` records it. `?scene=walk` (`WalkTestScene`) is lanes of bodies walking back and forth: forward, with a rifle, backward, sideways, diagonally, slowly, sprinting, hurt, and zombies (also shambling), a sprinter and a heavy. also zigzagging, and turning on the spot. `lanes=sideways,zombie` picks lanes, `follow` keeps the camera on the first walker for close ups, `prints` (P) marks where each foot lands (`FootprintMarker`: blue left, orange right, hollow for settling steps), `blood` puts a puddle of blood across every lane, `zoom=` and `speed=`; `npm run clip -- --scene walk --query "lanes=sideways&zoom=300&follow"`. `?scene=looks` (`LooksTestScene`) is every body the generator draws, in a grid, walking round little circles: the characters, the zombies, the heavies and Bob (`only=andy,santa` picks characters, `zombies=N`, `random=N` and `people=N` add new random zombies and living people, `still`, `zoom=`)
  - Muzzle flashes (`effects/MuzzleFlash.ts`) are drawn by a shader (`muzzleFlash.frag`) from the gun's `MuzzleFlashStyle` (`weapons/guns/muzzleFlashes.ts`, `GunStats.flash`): lobes of fire, each with ranges every flash picks from (so no two are alike, with their own random numbers), whose heat is added up, torn by noise streaming out of the muzzle, eaten away as it cools and colored by heat; the shape is the gun's character (the AR's prongs, the revolver's cylinder gap, the AK's slant brake, a shotgun's fat plume). They follow the muzzle while the gun recoils, and `SCALE` makes them all bigger than their styles. `?scene=flash` (`rig/FlashTestScene`, development only) is a column of guns firing in the dark (`gun=`, `speed=`, `zoom=`, `ambient=`); `gallery` holds flashes still, a row per gun (`columns=`, `age=0.3`, or `age=life` across the row)
  - `creature-stuff/` — `BodySprite` draws a body: head, torso, arms from the shoulders to the hands in two halves, bent at the elbow (`armReach.ts` bends each in 3D, the elbow out to the side and a little down, and the halves are drawn as foreshortened as they'd look from above; straight when the hand's out of reach), over the torso, whose ends are as round and wide as the arms' tops, so each arm grows out of its shoulder, and, given a `LegStyle` (`Legs.ts`: its look's leg and shoe textures and a `GaitStyle`), legs stretched from the hips to the ankles and shoes, under everything else. The legs follow its `Gait`, which is only looks, so it's moved on in `onRender` while the body's in view, by `game.simulatedTime` since the last time (nothing per tick, and nothing out of view), and posed with the rest in `updatePose`, each leg from its hip to where its foot is on the floor; standing square, the legs are under the torso and aren't drawn. Since the gait only moves on in view, landings out of view aren't seen (`onLand` doesn't fire for them); the shoulders twist a little against each step, and empty hands swing. Hip width and how far forward the foot is are in meters (`Legs.ts`, in proportion for bodies bigger or smaller than a human); the legs' thickness and the shoes' size come from the look. Humans, zombies, sprinters and heavies have legs, in their look's colors; crawlers and Bob don't, and corpses use the lying-down legs their look draws. The body's own images come from its look (`looks/`), as a `BodyTextures`: each anchored where it attaches and drawn at `BODY_PIXELS_PER_METER`, scaled for bodies bigger or smaller than a human, with the shoulders, arm thickness and head size in its `metrics`. Bodies with legs have `Shoes`: a foot landing in blood soaks its sole (and the other some), and the steps after leave prints, fainter each one until it's worn off (`PRINTS`, 10); `onFootLand` is for anything else that wants to hear about landings
  - `looks/` — bodies are drawn by code, not by hand: a `BodyLook` (`BodyLook.ts`: skin; build sliders from -1 to 1 for shoulders, chest, belly, bust, hunch, shoulder shape, arms, hands, head and legs; hair as sliders (coverage, volume, messiness, curls, length, hairline, parting, bun, ponytail, mohawk); eyebrows (bushiness, arch, tilt); a beard; a top (`TOP_STYLES`, color, secondary color, a pattern, a popped collar); sleeves; gloves; a hat (`HAT_STYLES`); glasses; `extras` (backpack, satchel, scarf, tie, sack, lanyard); hand-drawn `pieces`; trousers (`PANTS_STYLES`: trousers, jeans, shorts, a skirt) and shoes (`SHOE_STYLES`: sneakers, boots, dress shoes, heels, sandals, bare feet), each with a color; `zombie` (rot, blood, rips); and a `seed` for the random parts) is drawn by `drawBody` into an SVG `Drawing` per part (`parts/`: `head.ts`, `torso.ts`, standing and lying face down, `limbs.ts` for arms and hands, `legs.ts` for a leg, each foot and the lying legs, and `wear.ts` for patterns, rips, blood and grime), in millimeters round where each part attaches, facing +x. The house style (outlines, gradient shading, flat color: no texture but the zombies' rot) is `style.ts`, so changing it restyles everyone; it has presets to compare (`STYLES`: celNone, the default, cel shading with no outlines; cel and celLight with them; gloss, soft and minimal), which also hold the proportions (head size and shape, arm lengths, how arms bend), picked with `?style=` in the game or `--style cel,celNone` for the contact sheet, and numbers in one can be changed to try them (`cel:headRx=130;headRy=106`). `bakeBodies` draws every look the game needs at boot (while the rest loads, about 180 ms for 48 looks), puts their parts on atlas pages, rasterizes each page from one SVG, and makes the parts textures (`getAppearance(look)`: standing and lying `BodyTextures`, the walking legs' `LegTextures`, and the lying legs); looks have to be baked before anything is drawn with them, so a new kind of body adds its looks to the list in `main.ts`. Characters' looks are in their JSON; zombies (`ZOMBIE_LOOKS`, 48) and heavies (`HEAVY_LOOKS`, 8, built big) are random office workers (`randomLook.ts`: outfits by who they were, from shirt and tie to builder) made with their own generator and seed, so they're the same every run and don't touch the seeded one; Bob has his own (`BOB_LOOK`). `composeBodySvg` puts a whole body together as one SVG, standing or lying like a corpse (the editor's preview, `portraitUrl` for the encyclopedia, contact sheets). `pieces.ts` and `pieces/` are hand-drawn SVGs a look can wear on its head or torso (see `pieces/README.md`: 1 unit a millimeter, the middle of the page on the middle of the part, magenta and cyan recolored; templates in `assets/source/pieces/`), registered by `import.meta.glob` in `pieces/index.ts`. `hats/` holds hat styles drawn by hand instead of by code (the cowboy hat and the tricorn), recolored to the hat's colors (see the README). `npx tsx bin/look-sheet.ts [--zombies 24] [--people N] [--parts] [--pieces] [--only andy,chad] [--scale 200] [--style gloss,soft] [--standing]` renders a contact sheet of the generator's art to `tests/output/look-sheet.png` without the game
  - `effects/FloorStains.ts` — what's on the floor: blood splats and footprints, painted into 8 m textures made where they're needed (128 px a meter), so they stay for the floor and cost nothing to draw however many there are, and what's still wet. `splatBlood` (`effects/BloodSplat.ts`, for bullet hits and gibs) paints a splat and spills blood that's wet for 30 s; corpses' pools (still sprites, since they spread) are wet for two minutes. Wet spills are kept in a `SpillGrid` of 0.25 m cells, only where something's been spilled, and dry steadily from when they're spilled, so a foot landing reads the cell under it, and older blood soaks shoes less, then not at all. One per floor (`Persistence.Floor`), made by `getFloorStains` the first time anything's spilled, so every scene has one without setting it up. The footprint image is a placeholder SVG (`assets/source/legs/footprint.svg`), tinted
  - `items/` — what the store sells. Each `Item` (`Item.ts`: name, rarity, category, price, stacks, `apply`) usually changes a human's `PlayerStats` (`human/PlayerStats.ts`: multipliers and rule flags, neutral by default), which `Human`, `Gun`, `Bullet`, enemies, `Flashlight` and `VisionController` read at use time; `GunStats` stay shared and read-only. `ITEMS` (`items.ts`) is the pool: `equipment.ts` (placeholders ported from the old upgrades, plus items for one gun family like Buckshot Bounce) and `attachments.ts`. Attachments are owned by the human (`Human.attachments`) and go on whatever gun they `fit` (a family is an ammo class); for each slot (magazine, ammo, rail) a gun uses the newest one that fits (`Human.attachmentsFor`). Stat changes go through `Gun.effectiveStats(shooter)`, and rules (incendiary, piercing, exploding, and the family items' ricochets, last-round and long-range damage, kill refunds) are set on each `Bullet` as it's fired. Shelves lean toward attachments and items for the families you hold, and guns of the ones you don't (`OTHER_FAMILY_WEIGHT`); `giveItem` applies one and keeps score, and guns and throwables for sale are made up per shelf (`gunItem.ts`, with the trade-in of the gun a bought one replaces, and `consumableItem.ts`). A `passive` one (the exit stairs) only says what it is and never takes E

Anything `Flammable` (enemies, humans) can be set alight with `ignite()`, which adds a `Burning` child that hurts it over time (quietly: no blood or flinching), credits the kill to whoever lit it, and goes out on its own; lighting it again only keeps it burning longer. `FireGrid` (one per run, reset each floor) is fire on the floor: 0.5 m cells holding fuel (seconds of burning) that burn, use it up and light their neighbors that have fuel unless a wall is between them, so fire only goes where fuel was spilled (`spillFuel`, a flood fill that stops at walls, and `addFuelAlong`). Anything standing in a burning cell catches fire, and anything burning lights the fuel under it. Sources: the Incendiary Rounds and Dragon's Breath attachments (`Bullet.incendiary`) and molotovs (a consumable that `breaksOnImpact` and has `fire`, spilled and lit by `Detonation`). Looks: `FireRenderer` draws a soft blob of heat for each burning cell (bigger than a cell and nudged off its middle, so no grid shows) and burning thing into a low-resolution heat buffer over the screen, and `flames.frag` turns it into flames; each burning cell near enough to the view to light it has its own small flickering `PointLight` that wanders so its shadows move; `FloorMarks` paints fuel stains and scorch into level-sized textures; `FireEmbers` throws sparks. `SmokeField` is smoke: a density per fire grid cell that fire, burning things, gunshots (`GunStats.smoke`) and explosions (`ConsumableStats.smoke`) put in, which flows into neighbors with less unless a static wall is between them (doors hold it back by how shut they are), and thins out (a fraction, plus a fixed amount so it ends); `smoke.frag` draws it with churning noise and dark sooty patches, and bullets carve tunnels through it (`disturb`). All the numbers are in `fireConstants.ts`. Randomness for looks uses its own generator or time-based `flicker`, never the seeded one. In development, `?scene=fire` is a test room for fire (`FireTestScene`; `?auto` plays it by itself), and the backtick key shows smoke per cell (`FireDebugOverlay`)
  - `arena/` — `?scene=arena` (development only): a test room for trying characters and loadouts against enemies. The whole setup (character, weapon slots, items with stacks, throwable, usable, act, the wave's enemies, how they arrive (together, trickling in, surrounding the player, or `spread` evenly over the room), the layout (`hall` is a big one for stress tests, `offices` the same size divided into rooms, with as many walls as a real floor, `sprawl` the offices sixteen times over, 240 by 160 m, for how lighting holds up on a huge level), and options: can't die, unlimited ammo, dummies, fog, dark, doors (a door in each of the layout's doorways: `offices` and `sprawl` have them), `fires=N`, molotov-sized pools of fire spread over the room that never go out and come back after a clear, and `slowdown=N`, how many times slower than real bullets are: each gun's `muzzleVelocity` is the real gun's, divided by `bulletSpeed.slowdown`, 3 by default) is in the URL (`arenaConfig.ts`: `parseArenaConfig` / `arenaConfigToQuery`, names matched by `slug`), and Tab opens `ArenaPanel` to change it; applying resets the player with the loadout and rewrites the URL, so a reload or a copied link gives the same setup. Enter sends a wave, Backspace clears it (Shift: and resets the player). Enemies get the chosen act's scaling because `ArenaScene` is an `ActOverride` (`run/acts.ts`). Items are applied directly rather than with `giveItem`, so nothing is marked seen or saved
  - `lighting-and-vision/` — the `LightingManager` draws the `Light`s in view, all together, into a screen-sized texture cleared to the ambient color and multiplied over the world. Each light gets a square of an atlas (pages of two textures at `lightResolution` pixels per meter, the Lighting Detail setting, `LightAtlas.ts`); per page, one instanced draw call puts every light's shadows in the mask page (clipped to each light's square by `WEBGL_clip_cull_distance`), and one pass draws the lights' `lightSprite`s into the light page and erases what their masks cover; then one pass adds every light's square onto the screen with its brightness and color (`setIntensity`/`setColor`, free to change every frame). Lights are static by default: they keep their square in the `StaticLightAtlas` and are only drawn again when their setters (position, size, direction, source radius, shadows) or new walls mark them `dirty`; anything else that changes how one looks, like its `lightSprite` from outside, has to call `invalidate()`. Lights that change all the time are `dynamic` (fire, burning things, incendiary bullets, sparks, spit, the spitter's glow, night vision, the flashlight) and are packed into `LightAtlas` pages and drawn every frame. Flashes that stay put and fade (muzzle flashes, explosions) are static, so they're drawn once. So the cost per light is small and the number of render passes doesn't grow with them; a `gl.flush()` after them lets the GPU start right away (without it the stage's batches stall). Shadows come from `ShadowCasters`, which keeps the edges and interiors of every static `cast_shadow`-tagged shape on the GPU, in meshes by 16 m squares of a grid that are each only drawn for the lights they reach, so far walls cost nothing however big the level (rebuilt when the set of casters changes); its shaders (`shadowMask.vert`/`.frag`) turn each edge into its shadow from each light and work out per pixel how much of the light's disc (`sourceRadius`, at least a pixel, which antialiases hard shadows) it hides, so umbra and penumbra come from one calculation. Moving casters (doors, `cast_shadow` bodies that aren't static) shadow lights too: the ones reaching the lights in view are one more chunk, rebuilt when one of them moves, and the static lights where a door moved are drawn again (`StaticLightAtlas.invalidateArea`); a static light that's been out of view is drawn again when it comes back, so doors out of view cost nothing. Closed doors block light. Vision is fog of war and works the other way round: `visibility.ts` casts rays from the player to build the visible region as an angle-sorted polygon (pure geometry, node-tested, with per-occluder transmission so tinted glass can come later), `visionMesh.ts` turns it into meshes that darken everything outside it with penumbra wedges, `VisionController` renders those into a texture around the player and draws it dimmed (what you've seen but can't see now), and `ExploredMap` remembers where the visible region has been in a level-sized texture and draws black over the rest. `VisionController.visibilityOf(point)` tells anyone whether the player can see a point; enemies fade out with it. Humans carry a `DirectionalLight` flashlight (`human/Flashlight.ts`), off until toggled and mounted under the barrel of the gun in hand. Contact shadows (soft darkening where walls, doors, door frames and elevator doors meet the floor) are `ContactShadows`: each `ContactShadow` is a rectangle with a reach, nine quads of a generated texture (`contactShadowTexture.ts`) cut like a nine-slice, drawn into a half-resolution texture over the screen in the "min" blend mode, so where shadows overlap the darkest wins and they join up at corners instead of darkening twice; then a mesh of the 0.5 m cells any shadow can reach (each once) multiplies the floor by it on `Layer.FLOOR_AO` (`contactShadows.vert`/`.frag`). Static ones are meshes in 16 m chunks built when they change; a moving one (a door) has its own small mesh that's only moved, and its cells are its whole swing, or an `area` it's given (an elevator door, whose shadow `setSize`s as it slides). Shadows aren't painted into wall or door images any more; new props can add a `ContactShadow` instead

  - Sounds are kept as full-quality `.flac` (or `.wav`) and referred to as such everywhere; `vite-plugins/encodeAudio.mts` encodes them to Opus `.ogg` in `npm run build`, with `ffmpeg-static`; the dev server serves the originals. ## Architecture conventions

- Everything in the game is an `Entity` (usually `extends BaseEntity`) added with `game.addEntity(...)`. Entities optionally declare `body`/`bodies`, `sprite`/`sprites`, `springs`, `constraints`, `children`; the `Game` registers those with physics/rendering on add and cleans them up on `destroy()`.
- Child entities: use `this.addChild(entity)` so they are added/destroyed with the parent.
- `this.game` is always a `Game`; reading it while the entity isn't in a game throws. Use `this.isAdded` / `this.isDestroyed` for the rare cases where that's possible (setup before `game.addEntity`, or something that can be hit again in the physics step it was destroyed in, like `Enemy.die`). Code after `await this.wait(...)` never runs once the entity is destroyed, so it needs no guard.
- **Events are methods named `on<EventName>`, marked with `@on("eventName")`.** The decorator registers the handler (undecorated `on*` methods are never called), checks that the name matches, and type checks the payload. Built-in events are in `core/entity/BaseGameEvents.ts` (`onAdd({ game })`, `onAfterAdded`, `onBeforeTick`, `onTick(dt)`, `onAfterPhysics`, `onRender(dt)`, `onLateRender`, `onPause`, `onUnpause`, `onDestroy({ game })`, `onResize({ size })`), `IoEvents.ts` (`onKeyDown({ key })`, `onButtonDown({ button })`, `onMouseDown`, ...), and `PhysicsEvents.ts` (`onBeginContact({ other, ... })`, `onImpact`, ...).
- Custom game events are declared with their payload types in `src/config/CustomEvent.ts`, dispatched with `game.dispatch("levelComplete", undefined)` / `game.dispatch("startLevel", { level })`, and handled by an `onStartLevel({ level })` method.
- By convention `on*` names are only used for decorated event handlers; direct-call hooks use other names (`hitByBullet`, `handleDeath`, `handleInteract`).
- `onTick` runs in tick layers (`src/config/tickLayers.ts`: `input`, `main`, `enemies`, `effects`, `fire`, `camera`, in that order), and `onRender` is grouped the same way (in an entity's first layer). An entity picks one with `tickLayer = "camera" as const`; one that doesn't is in its parent's layer (so `BaseEnemy` puts its controller, sprite and voice in `enemies`), else `main`. The camera follows in the last layer so it sees final positions. The profiler times each layer as a whole, so they're also how the frame's time is sorted into categories: put anything new that there can be many of in the layer it belongs to.
- The tick rate follows the display (60, 120, 144 per second...), so anything that changes per tick scales with `dt`: velocities times `dt`, smoothing as `Math.pow(kept, dt * 60)`, never a fixed amount per tick.
- `onRender` is only for how things look: nothing else may depend on it having run, since things out of view skip it. Anything there can be many of checks `this.game.camera.isInView(position, radius)` first and, out of view, hides its sprite (with `renderable`, or `visible` if nothing else uses it) and returns (`BodySprite`, `BaseEnemy`'s fade, `SpeakingCircle`, `Bullet`, `Spark`). State other code reads comes from bodies, or is brought up to date when asked for (`BodySprite.getPartPoses` poses the body first).
- Sprites choose their render layer via `sprite.layerName = Layer.X` (`src/config/layers.ts`, ordered bottom to top). Use a Pixi `Container` (not an empty `Sprite` or a `Graphics`) as a parent for other display objects. Position sprites from vectors with `sprite.position.copyFrom(v)`.
- **UI is HTML, the world is Pixi.** Menus, screens, and HUD text extend (or add a child) `ReactEntity`, whose `getReactContent` returns Preact JSX; it re-renders every frame, so components just read game state (`this.game.io.usingGamepad`, `getVolumeController(game).muted`) instead of tracking it through events, and fades are fields driven by `this.wait(...)` callbacks. Shared button components live in `menu/MenuButtons.tsx`; styles are plain CSS files imported for their side effect (`import "./menu.css"`), with `.menu-screen` as the full-page, `pointer-events: none` root that buttons opt out of. Fonts from the manifest are registered as `FontFace`s, so `font-family: captureIt` works in CSS. Text positioned in the world (floor labels in `TutorialRoom`/`SpawnRoom`, `SpeakingCircle`) and texture-based HUD (ammo shells) stay Pixi. Subclasses that override `onAdd`/`onRender` must call `super`.
- Fast entity lookup: `game.entities.getSingleton(LevelController)` / `getByConstructor(Cls)` (exact class), `getTagged(tag)`, `getById(id)`, or type-guard filters registered with `game.entities.addFilter(isHuman)` and read with `getByFilter(isHuman)`.
- `persistenceLevel` (see `Persistence` in `highrise/constants/constants.ts`) controls what `game.clearScene(threshold)` removes.
- Assets are referred to by name (camelCased file name without extension): `Sprite.from("andyHead")`, `new PositionalSound("wallHit1", position)`, `fontName("captureIt")`. Names are type checked against the manifest (`ImageName`, `SoundName`, `FontName`), so type arrays of them accordingly. Names must be unique per asset type; the manifest generator fails loudly otherwise.
- Stats-as-data: guns, melee weapons, consumables, decorations, zombie variants, and items are plain objects in their own files, collected in an index (`gunStats.ts`, `weapons.ts`, `consumableStats.ts`, `decorations.ts`, `items.ts`). Characters are JSON (see `characters/data/` above). macOS file names are case-insensitive, so an index can't sit next to an interface of the same name (`GunStats.ts` vs `gun-stats/gunStats.ts`).
- All randomness goes through `core/util/Random.ts` so that `?seed=123` makes runs reproducible. Don't call `Math.random()` directly, and don't consume randomness at module load time (the seed is applied in `main()`, after modules have run): `ShuffleRing` shuffles lazily for exactly this reason.
- `process.env.NODE_ENV === "development"` gates `CheatController`. It also gates `?play`, which skips the title and lobby and starts a run right away (`?play=chad` picks the character, else the last one played; `?floor=5` starts on that floor, 0 being the tutorial). `window.DEBUG.game` and `window.DEBUG.profiler` expose the game and the profiler in the console.

## Profiling

- Backslash cycles the corner `StatsOverlay` (`core/util/stats-overlay/`, a `ReactEntity`): off → fps (just the frame rate; the Show FPS setting starts it there) → lean (fps + counts) → profiler (per-frame CPU breakdown; `?profile=1` starts there; `R` resets, `P` pauses profiling) → render. Shift-Backslash goes backwards. Panels implement `StatsPanel`; add one to the list in `main.ts`. The breakdown is a tree: `Game.nextFrame` → `Game.tick` (per tick layer, per entity class) / `World.step` (broadphase, narrowphase, solver) / `Game.render` (per tick layer, per entity class, then `Renderer.render` for Pixi). Numbers are smoothed ms per frame.
- The profiler is `core/util/Profiler.ts`. Add sections with `@profile` on a method or `profiler.measure("label", () => ...)`; they nest under whatever is running. Per-entity timing only happens while `profiler.entityDetail` is on (the profiler panel and `captureProfile` turn it on), because it costs a couple of `performance.now()` calls per entity per tick. That's about 0.4 µs a call, which with hundreds of entities is milliseconds (at 800 zombies it more than doubled the `enemies` layer), so take totals from a capture without it (`captureProfile(page, ms, { entityDetail: false })`) and use per-class numbers only to compare classes.
- For exact numbers rather than smoothed ones, `profiler.startCapture()` / `stopCapture("Game.nextFrame")` average over a window; that is what `npm run benchmark` and the `captureProfile` test helper use.
- `Renderer.render` is the CPU side of Pixi only. The GPU side is `core/util/GpuProfiler.ts` (WebGL timer queries; `gpuProfiler.measure(label, fn)`, or `measureCpuAndGpu` for both profilers under one label), which times `Game.render`, split by tick layer, `lateRender` and `Renderer.render`, and the lighting's and vision's passes. Its results come back a few frames late. Only the total is trustworthy: in Chrome on a Mac, timing sections separately adds about 0.25 ms each and counts passes the GPU overlaps twice (at 32 fires the sections added up to 17 ms against 7 ms for the whole), and every number includes the GPU waiting on the CPU mid-section, so it's an upper bound. To find what something costs the GPU, compare the total with it on and off (the lighting benchmarks do). The profiler panel shows the sections while it's open; `captureProfile` returns `gpu` (just the total, unless `gpuDetail`). Things drawn as part of the stage are timed with `gpuTimed(label, content)`, a container with a `RenderContainer` on either side that starts and ends the section (the fire's flames, embers and smoke, and the floor marks), and the fire benchmark prints the sections; on a Mac they come out about equal whatever they draw, so they're only a hint there. For what one draw really costs, draw it many times inside a single timer query.

## Physics

- Bodies come from factories: `createRigid2D({ motion: "dynamic" | "kinematic" | "static", ... })`, or `createPointMass2D(...)` for things that should never rotate from collisions (humans — their `angle` is set directly).
- Pairs are only collision-tested if at least one body is dynamic. A sensor-like body that you move by hand but that must detect static things is a dynamic body with `mass: 0, collisionResponse: false` (see `SwingingWeapon`).
- There is no gravity. Friction comes from actual contact forces.
- The broadphase (`SpatialHashingBroadphase`) keeps two hashes: static bodies, hashed once when added, and everything that moves, rebuilt after each step (lazily, by the first query or the next step's broadphase) and kept up to date as bodies are added or removed in between. So queries and raycasts during a tick cost nothing per body in the world, and see moving bodies where the last step left them. Moving a body by hand doesn't update its AABB (or its place in the hash) until the next step, same as before. `aabbQuery(world, aabb, false)` asks for static bodies only. Raycasts get their candidates from `rayQuery`, which walks the grid cells along the ray rather than taking its whole bounding box.
- `game.world.raycast(from, to, { collisionMask, filter, skipBackfaces })` returns the closest `RaycastHit` or `null`. `collisionMask` is matched against the shape's `collisionGroup` only; to respect a shape's own `collisionMask` (e.g. fences that let projectiles through) use `filter` — see `projectileRaycast`.
- Boxes can't be resized; replace the shape (see `ElevatorDoor`). Concave colliders: `convexShapesFromPolygon` in `core/physics/utils/polygonShapes.ts`.
- Vectors are `V2d` (`core/Vector.ts`), an `Array` subclass so it is compatible with `[x, y]` tuples. Methods prefixed with `i` mutate in place (`iadd`, `imul`); the others allocate.

## Rendering gotchas (Pixi 8)

- Filters nested inside another filter render nothing if their `resolution`s differ. The stage-level damage filter in `DamagedOverlay` uses `resolution: "inherit"` for this reason.
- Custom filters are GLSL ES 3.0 for the WebGL renderer (`damage-filter.frag`), imported as a string with `?raw`.
- A `GlProgram` is compiled as GLSL ES 3.0 only if its fragment shader contains `#version 300 es`; otherwise Pixi compiles it as ES 1.0, quietly `#define`-ing `in`/`out`/`finalColor` into the old keywords, so ES 3.0-only features (`flat`, `gl_ClipDistance`, integer attributes) fail with odd errors. Start shaders that need them with `#version 300 es` (`shadowMask.vert`/`.frag`). Extension directives have to come before any code, which Pixi puts its own lines in front of: `ShadowCasters` patches one in after the version line.
- Rendering into textures mid-frame (`LightingManager`, `Light`, `Shadows`) uses `renderer.render({ container, target, clear })`. Pass `clearColor: [0, 0, 0, 0]` or the target is cleared to the opaque canvas background. Filters don't work inside such a pass (they size themselves to the canvas, not the target); apply them on the stage instead, or avoid them altogether the way vision does (soft edges as mesh geometry).
- `renderer.width`/`height` are logical pixels in Pixi 8; don't divide by `resolution` again (that bug broke the Low quality of old, which halved the resolution like a render scale of 50%).
- The canvas's antialiasing is fixed when it's made: it's the player's Antialiasing setting (`antialiasFor` in `settings/settings.ts`; Auto is off on displays with two or more pixels per point, where it buys little and costs a few tenths of a millisecond a frame at resolution 2, mostly in full-screen passes like the damage filter), applied the next time the game starts; `?aa=0` / `?aa=1` override it. Pixi's own ticker is off (`autoStart: false`): the game draws each frame itself, and the ticker drew the stage a second time.
- In a `renderer.render({ container, target })` call the root container's own `blendMode` is ignored; wrap it in a `Container` if it needs to erase or add. And `RenderTexture.resize` doesn't update the texture coordinates of sprites already using the texture, so a texture that changes size (`ExploredMap` per level) is created afresh and reassigned.

## Misc gotchas

- `src/index.ts` must import `core/Polyfills` first.
- The manifest imports each asset with `?url`, which is what gives it a hashed file in a build. In development `vite-plugins/plainManifestUrls.mts` rewrites those imports into plain URLs, because each would otherwise be a module the browser fetches before the game starts (800+ of them).
- JSX is Preact (`jsxImportSource` in `tsconfig.json`, which Vite reads too).
- Fullscreen is requested on `document.documentElement`, not the canvas, so the HTML overlays stay visible. The desktop app skips that and uses the window's own fullscreen, which Escape doesn't leave.
- Pixi resolves asset URLs itself and only understands http(s) origins, so under `app://` a root-relative `/assets/x.png` becomes `app://assets/x.png`. The preloader hands it absolute URLs.
- Playwright can't drive the packaged app, because its fuses (`forge.config.ts`) turn off the debugging Playwright needs; `tests/electron/` drives the built but unpackaged app and only smoke-launches the packaged one.
- The repo is large (~800MB of git history, mostly binary assets). Avoid broad globbing/searching under `resources/` and `assets/`.
